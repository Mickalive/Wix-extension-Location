### B1 — Compile error in domain core: `wallClock.ts` imports a non-existent export
`src/domain/time/wallClock.ts` line 20:
```ts

```
`isValidWindowStartMinute` is exported from `src/domain/model/primitives.ts`, not from `time/intlZone.ts`.
`tsc` reports `TS2305`; under Vitest SSR the import binds `undefined` and every call raises
`TypeError: isValidWindowStartMinute is not a function` at `wallClock.ts:39`, cascading through
`resolveSlot` → `tests/helpers/builders.ts#factsAt` into nearly every suite.
**Reproduce:** any strict typecheck of the candidate, or `npx vitest run` in a harness → 61 failing tests across 7 files.

This finding also proves the builder never executed its own tests or a typecheck before submitting.

### B3 — Five red assertions remain after load repair; four are provably wrong TESTS, and they leave the identity-key conflict path unproven
Ground truth established by direct computation (contract §4.7 semantics):

1. `duplicates.test.ts` → *"blocks a second same service/day overlapping slot"* (line ~57): comment claims

   fixture booking is 13:00Z–14:00Z ⇒ no overlap ⇒ `'allow'` is the CORRECT outcome. Test fixture is wrong, not the code.
2. Same file, *"blocks across services when the SAME key is supplied"* (~line 135): identical wall-time/UTC confusion

   two tests designed to fire the identity-key conflict path; with broken fixtures, `IDENTITY_TIME_CONFLICT` has zero
   passing coverage and acceptance criterion 5 is unproven. Fix fixtures so instants genuinely overlap (e.g. keep the
   existing booking at 17:00Z–18:00Z, or request `factsAt(WED, 540, 600)` against the 13:00Z booking), keeping the
   same-service/no-key negative controls meaningful (see A4).
3. `localDate.test.ts` line ~33: expects `2026-03-09T02:30:00Z` → 21:30 "EST" (1290). US DST began 2026-03-08; New York

4. `wallClock.test.ts` line ~37: expects nonexistent 02:30 spring-forward → 07:30Z ("03:30"). Contract §4.7 says advance
   to the **next valid local time** = **03:00 EDT (07:00Z)**, which the implementation returns. Note the same file's

in cases 3–5 the implementation already matches the Technical Contract.

### B4 — Implementation defect: slots ending exactly at local midnight are always falsely blocked
`src/domain/evaluate.ts` stage 4 (line ~152):
```ts
} else if (endDate !== targetDate) {
  violations.push(outsideHours(..., 'overnight_slot'));
}
```
A slot ending at exactly local midnight has `endDate = targetDate + 1 day`, so it is rejected as `overnight_slot` even
when a configured window ends at minute 1440 — which the model itself declares legal (`primitives.ts`: "1440 is legal
only as an exclusive window end"; `validateRuleSet` accepts `{startMinute:0,endMinute:1440}`; `resolveSlot` explicitly
supports `endMinute=1440`; `splitWindows.test.ts` exercises a `[0,1440)` window). Empirically proven in my harness:

```
rules: weeklyWindows.locations['loc-1'].wednesday = [{startMinute:0,endMinute:1440}]
evaluateRules({svc-1, loc-1, start:2026-08-27T03:30:00.000Z, end:2026-08-27T04:00:00.000Z})  // 23:30–24:00 EDT Wed
⇒ decision 'block', OUTSIDE_BOOKING_HOURS, details {startMinute:1410, endMinute:0, reason:'overnight_slot'}
```
Customer impact: any business open until midnight gets false customer-facing rejections for legal end-of-day slots
(e.g. 23:00–24:00). This contradicts the module's own documented semantics and will surface in gates T-WH*/T-VP*.
**Fix:** treat an end instant landing exactly on local midnight as `endMinute=1440` for window fitting (only when
`endDate !== targetDate && minutesOfDayOfInstant(endMs)===0`), keep genuine overnight spans blocked, and add a
regression test: slot 23:30–24:00 under `[0,1440)` must ALLOW; slot 23:30–00:30 must block as overnight.
